Production Multi-Tenant Agent：把 Tenant Isolation 做成控制面 §10.T

真正的多租户边界不是用 Prompt 告诉模型不要看别人数据，而是：即使模型、Router 或 Tool Arguments 出错，Tenant A 的执行仍然无法读取、修改、调用或推断 Tenant B 的受保护资源。

FIG.10.T1 · TENANT ISOLATION CONTROL PLANE

Tenant Context 必须从身份层贯穿到每一个资源访问点

tenant_id 是可信安全上下文，不是允许模型自由改写的 Agent State。

01 · IDENTITY

User / Service → Trusted Tenant Context

Identity Provider 解析 user / service identity，并绑定 tenant_id、role、entitlement。Prompt 和 LLM output 不能覆盖这个上下文。
02 · POLICY

Principal + Tenant + Action + Resource

Authentication 只回答是谁；Authorization 判断动作；Tenant Isolation 继续限制这个执行永远只能触达哪个资源宇宙。
03 · RUNTIME

State · Memory · RAG · Tools · Cache · Jobs

每个共享面都必须 tenant-scoped：Checkpoint、Retriever、MCP credential、Queue envelope、Cache namespace、Sandbox 与 Trace 都不能丢失租户上下文。
04 · RESOURCE

Storage Policy · Credential Broker · Namespace · RLS

最终资源层继续 fail closed：数据库、对象存储、Vector Store 和外部 SaaS 通过 policy、namespace、RLS 或 tenant-scoped credential 做第二道边界。
05 · VERIFY

Audit · Negative Tests · Quotas · Fairness

上线验证不只测自己能访问自己，还要主动猜别人的 thread/document、篡改 tenant context、碰撞 cache、重放 checkpoint，并做 per-tenant noisy-neighbor load test。
核心原则

The agent may be wrong; the infrastructure must still make cross-tenant access fail closed.

FIG.10.T3 · DEPLOYMENT SPECTRUM

Pooled / Bridge / Silo 是逐资源的选择，不是整个系统一个开关

POOLED

Shared Runtime + Logical Isolation

高利用率、低成本；要求强 tenant policy、严格 credential boundary 和持续 cross-tenant test。
BRIDGE

Shared Control Plane + Selective Isolation

默认 pooled；按 tenant、risk、tier 或 compliance 给特定 storage / compute / sandbox 独立资源。
SILO

Dedicated Resource Boundary

更小 cross-tenant blast radius，但增加成本、容量碎片与 fleet lifecycle 复杂度。
不要漏掉性能隔离

Tenant Isolation 不只防数据越界。共享 LLM、Queue、Tool API、Cache 和 Sandbox 还需要 per-tenant / tier concurrency、token、tool、storage 与 cost budget，避免 noisy neighbor。

外部核验日期：2026-09-23。实现例包括 AWS multi-tenant agentic AI guidance、PostgreSQL Row-Level Security、Pinecone namespaces 与 vLLM prefix-cache salting；这些是具体实现证据，Handbook 的核心规则仍然是 vendor-neutral 的 tenant-isolation control plane。
