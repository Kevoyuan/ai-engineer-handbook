两个面试常见生产事故：Tool 超时并不证明操作失败；多层重试可能把故障放大成系统雪崩。

SOURCE BOUNDARY

Q8 · Agent 创建发票超时，能不能直接重试？

不能假设第一次没执行。由可信 Host 为同一业务操作分配稳定幂等键，先确认下游支持幂等，再用同一键/参数重试，或查询操作状态和人工核对。

Agent request → trusted host + operation ID
  → authorize → durable intent → tool call
  → timeout: outcome UNKNOWN
  → query status / retry SAME operation key
  → reconcile → one business effect

Stripe 文档的首个结果复用（包括 500）、参数一致性检查和至少 24 小时后的 key 清理是该服务自身的行为，不可推广到所有 CRM / Payment API。

Q9 · 为什么用了 Exponential Backoff 仍然造成雪崩？

失败请求仍消耗服务容量。三个独立调用层各自最多三次尝试，理论最大尝试放大到 27 次；这是示意计算而非实测。若客户端同时按固定间隔重试，就会形成同步洪峰。

控制生产作用
Retry budget限制尝试数和总耗时
Jitter打散同步重试洪峰
Circuit breaker阻止持续向故障依赖发请求
Backpressure / shedding限制无界队列并显式拒绝过载
核心判断

优先让一个层级拥有 Retry 决策，选择可安全重复的操作，配合 deadline、随机抖动与降级，而不是靠多层无限补救。
