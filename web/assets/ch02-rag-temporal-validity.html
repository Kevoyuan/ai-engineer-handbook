RAG 时效治理：索引新鲜与业务有效期 · §2.11

source-to-query freshness 衡量更新何时可查；业务有效期回答在用户所问的时间点，哪条事实生效。刚入库的历史公告可能早已失效，旧文档中的长期规则也可能仍然有效。只按 indexed_at 或发布时间降序会混淆两者。

证据应区分 source_record_id、document_version、source_updated_at、indexed_at、effective_from、effective_to、supersedes、业务 scope 与权威来源。字段由业务源确认，不能凭检索分数推断当前有效。价格、库存、权限和实时状态优先查询权威实时系统；索引仅在约定的新鲜度窗口内充当读模型。

执行顺序：查询意图 + as_of 时间 + 授权 scope → 权威来源与所需快照 → 过滤无效或被替代证据 → 检索与同一事实的版本冲突消解 → 携带证据 ID、版本、生效区间回答 → 在 fetch / answer 边界复查关键依据。提示词只能辅助，不能代替这些可执行约束。

默认查当前与显式历史回溯使用不同的 as_of。新版可能尚未生效，最高版本号不能一概覆盖当前版本。发布、撤回和改正也可能乱序到达，需要稳定 ID、版本或序列、可重放增量处理，以及索引可见性与缓存失效检查。

关键权威事实无法确认时，尤其在高风险决策中，应标明未知或拒绝确定性结论。底层受限时可在检索后过滤，但候选窗口不足会漏掉合法证据；后过滤不能代替权限边界或源端核验。

必须覆盖四类坏例：新版已生效仍引用旧片段；新版未生效却被提前引用；源已撤回但索引或缓存仍可见；明确查历史却只返回当前版。分别测 source-to-query lag、过期证据引用率、同一事实版本冲突率和带正确 as_of 的答案支持率。

本节是 §2.5、§2.8、§2.10 与第 4 章证据充分性规则的工程综合。原始面试稿未提供出处；时态向量库隔离、跨源与向量索引的同一事务都不是通用前提，必须按具体存储和业务源的一致性契约设计。
