Cost per Successful Task：优化任务成本，而不是单次模型价格 §9.13

模型更便宜，不代表任务更便宜。弱模型如果带来更多重试、更多轮次、更多检索和更长上下文，总 Token 消耗可能上升，最终把单任务成本推高。新的 Production Monitoring 课程进一步补上成本记账层：Usage 必须先被正确采集和定价，才能可靠地进入 Cost / Task 与 Cost / Successful Task。

FIG.9.C2 · COST ACCOUNTING

Usage 不是 Cost：必须经过价格解析，再与 Task Outcome 连接

成本观测的关键是把“用了多少”与“按什么价格计费”分开保存，否则价格变更、Cache Read、Custom Model 和非 LLM 组件都会让历史分析失真。

1 · CAPTURE

Usage Capture

记录 Input / Output / Other，以及 cache_read、reasoning 等 subtype；Tool、Search API、Retrieval 等需要自己的计量或 literal cost。
2 · PRICE

Pricing Resolution

用 Model / Provider / Token Type / Effective Date 匹配价格。具体 subtype 先计价，剩余 Usage 再按默认价格计算，避免重复计费。
3 · JOIN

Aggregate + Outcome

Run Cost 汇总成 Trace / Task Cost，再按 Model、Tool、Customer、Version 等切片，最后与 Task Success 连接得到真正可优化的 Cost / Successful Task。
成本类别来源课程的 Breakdown工程读法
InputPrompt · text/image input · cache reads定位 Context、Prompt Prefix、Tool Schema 与 Prefill 成本。
OutputGenerated text/image · reasoning tokens定位输出长度、Reasoning 与 Decode 成本。
OtherTool · retrieval · custom run补齐 Search API、Database、Retrieval 等非 LLM 成本，避免把 Token Cost 误当总任务成本。
CACHE READ ≠ COST HOTSPOT

课程强调 Cache Read Token 通常比普通 Input Token 更便宜，因此 Cache Read 即使占 Input Token 的大头，也不代表它占 Input Cost 的大头。正确分析单位是 Token Type × Effective Price，而不是只看 Token Share。

PRICING VERSION BOUNDARY

来源课程说明 LangSmith Model Pricing 更新不是 retroactive，只影响更新后记录的 Trace。跨时间比较成本时，应明确保存 Pricing Effective Date / Version，并区分“当时实际计价”与“按统一价格表重算”的分析口径。

ACCOUNTING RULE

Measure usage separately from pricing, then join cost with task outcome.

CANONICAL RULE

Optimize cost per successful task, not price per model call.
