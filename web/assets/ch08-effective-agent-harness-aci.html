Effective Agent Harness：Simplicity · Transparency · ACI §8.Z

优秀 Agent 不是“最强模型 + 最多工具 + 最复杂框架”。模型提供能力上限，Harness 决定 Context、Tool、State、Environment Feedback、Validation 与 Human Control 如何把能力转成稳定执行。

FIG.8.Z1 · EFFECTIVE AGENT PRINCIPLES

Anthropic 的三原则可以直接落成 Harness 设计问题

SIMPLICITY

只为真实 failure mode 增加复杂度

single call → tool loop → workflow → graph → multi-agent。升级必须能解释解决了哪个 state、recovery、permission、parallelism 或 observability 问题。
TRANSPARENCY

展示 Plan · Action · Evidence · State

透明不是暴露 hidden CoT，而是让 todo、工具调用、结果、diff、测试、retry、approval 与 completion evidence 可观察、可纠偏。
ACI

Agent-Computer Interface

Tool name、schema、参数语义、错误模型与返回证据本身就是 Prompt Engineering；重复错误优先通过 interface constraint 消除。
FIG.8.Z2 · HARNESS CONTROL LOOP

模型输出不是完成证据，Environment Feedback 才能闭环

1

Plan / Decide

选择下一步，不把规划本身当真相。
2

Tool / Action

通过清晰 ACI 执行 bounded action；Host / Policy 保留真实权限。
3

Observe Ground Truth

tool result · test · diff · browser observation · retrieval evidence · policy result
4

Update State / Verify

根据真实环境证据继续、修复、回退、升级或停止。
5

Trace → Eval → ACI Repair

把重复工具错误聚类，修 name/schema/default/error message/validation，再跑 regression。

工具最小化

Minimize overlapping ways to express the same action. 目标是减少语义重叠和选择歧义，不是机械追求 tool count 最小。

透明边界

Expose plans, actions, state transitions, evidence, and concise reasoning summaries when useful. 不要让系统依赖 hidden Chain-of-Thought 才能调试或审计。

FIG.8.Z4 · HARNESS EVOLUTION

模型越强，Harness 不一定越少：它会从“代偿”迁移到“治理”

部分旧逻辑会被 Model / Provider Runtime 吸收，但 autonomy、blast radius 和真实资源访问越大，系统越需要明确的权限、状态、成本、审计与恢复保证。

COMPENSATORY HARNESS

弥补模型能力缺口

format repair · rigid retry loops · weak-planning scaffolds · argument normalization · basic self-correction
GOVERNANCE / RUNTIME HARNESS

约束更强的行动能力

permission · sandbox · durable state · budget · timeout · audit · approval · recovery · tenant boundary
MODEL CAPABILITY ↑

一些补偿逻辑被模型 / SDK / Provider Runtime 吸收

structured arguments · tool dispatch · handoffs · sessions · simple retry/self-correction · built-in shell/computer primitives
AUTONOMY / BLAST RADIUS ↑

系统保证变得更重要，而不是更少

谁能做什么、状态是否持久、成本是否受控、失败如何恢复、动作能否审计，这些都必须由 runtime contract 明确承担。
问题 模型能力 Harness 保证
能不能想出下一步？planning / reasoning—
允不允许做？—permission / policy / approval
崩溃后还能继续吗？—state / checkpoint / reconciliation
会不会无限烧钱？—budget / rate / timeout / cancellation
出了问题能解释吗？—observable trace / artifact / evidence
最终原则

Model improvement removes some scaffolding; it does not remove the need for runtime guarantees.

TRACE BOUNDARY

记录 observable trajectory：tool calls、handoffs、guardrails、state transitions、errors、artifacts、latency/cost；不要把 private hidden Chain-of-Thought 当成 Harness 必须落盘的数据。
