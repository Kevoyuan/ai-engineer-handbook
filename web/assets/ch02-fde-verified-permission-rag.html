Permission-Aware RAG：三道有证据的面试题 §2.FDE

企业 RAG 最危险的失败未必是召回不足，而是越权读取。区分授权身份、候选集过滤、检索质量与数据权限更新。

SOURCE BOUNDARY

以下是根据 FDE 网站公开考点独立撰写的问题与答案，不是付费题目的官方答案。产品细节以链接的官方文档为准；设计建议属于 Handbook 综合判断。

Q1 · 如何确保 RAG 不泄漏其他租户的文档？

由可信服务验证身份并计算有效权限，在检索前约束合法候选集；授权通过后才能进入 rerank、LLM context、缓存与日志。模型不能自行决定谁有权限。

Trusted caller identity → policy/tenant scope
→ authorized retrieval candidates
→ authorized rerank → evidence → answer
→ tenant-scoped cache, redacted traces
风险必须验证
混合租户文档候选集、Prompt、日志全部不出现越权文档
旧 ACL / 共享缓存撤权后缓存与源内容一致地拒绝访问
模型传入 tenant_id请求身份不得由模型覆盖
核心判断

Security filter 是查询条件，不是认证机制。Azure 文档明确说明基于字符串的 security-trimming 不提供身份认证本身。

Q2 · 向量检索的 Pre-filter 与 Post-filter 哪个更可靠？

当用户只可见 1% 文档时，先全局 top-k 后过滤可能得到空结果，即使可访问集合内有答案。Pre-filter 可改善授权集合内召回，但高度选择性的过滤可能增加 ANN 遍历成本。

方法效果与取舍
Pre-filter合法候选集内检索；选择性高时成本上涨
Post-filter先 ANN 后过滤；小 k 易漏掉合法相关文档
Strict post-filter（预览）全局 top-k 后过滤；对高选择性权限风险最大

Q3 · 权限撤销之后如何防止旧索引仍然放行？

追踪源权限到索引的同步窗口，必要时在取回源文档时重新授权；建立撤权到拒绝的 SLO，并对缓存、异步任务和引用执行隔离。无法确认权限版本时对敏感资源 fail closed。

核心判断

最关键的回归测试：Alice 已撤权，搜索索引、缓存和下游工具都不能再次向她提供旧文档。
