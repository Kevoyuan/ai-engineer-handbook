推理服务、部署、安全与 AI 平台

SERVING · K·P·S·M
WWHENTTRADE-OFFMMETRIC

Agent 应用最终落到推理系统上。到了 Serving 层，“多个 Agent 能否共享 KV Cache”不再是简单的 yes / no，而取决于请求是否具有兼容且完全一致的 token prefix，以及 inference engine 的 cache key、生命周期和 isolation policy。

FIG.10.1 · PREFIX KV REUSE

共享的是已计算前缀，不是一个可变会话对象

Prefix Cache 命中后只跳过共享前缀的 Prefill；分叉后的 suffix 和后续 Decode 仍属于各自请求。

01

Shared Prefix

System Prompt · Tool Schema · Stable Policy → 完全一致的 token prefix
02

Prefix Cache Lookup

Radix tree / block hash 等机制找到最长可复用前缀
03

Prefill Suffix

只计算未缓存的 Agent-specific / User-specific suffix
04

Decode

每个请求继续自己的 token-by-token generation
核心边界

Prefix caching primarily reduces Prefill / TTFT; Decode remains a separate cost.

10.1 Prefill、Decode 与两种 KV 复用

机制复用范围主要价值
Within-request KV Cache同一请求已处理 token避免 Decode 时重复计算全部历史
Cross-request Prefix Cache不同请求之间兼容且完全相同的 token prefix避免重复 Prefill，降低 TTFT

没有跨请求 Prefix Cache 时，相同前缀通常仍会被各自 Prefill。现代 serving engine 是否默认启用、如何索引和何时淘汰都取决于 engine、version 与 config，因此不要把“默认不能共享”当成通用事实。

10.2 Cache Hit 需要 token-level identity

KEY常见兼容条件
model / revision · tokenizer · chat template · exact token IDs · position semantics · adapter / LoRA · multimodal identity · cache namespace / salt · block granularity
MISS常见命中率杀手
动态 timestamp / request id · Tool Schema 顺序变化 · 不稳定 JSON serialization · tenant 信息过早注入 · role prompt 过早分叉
PROMPT LAYOUT

Prefix Cache 的命中率部分取决于应用层 Prompt Layout。把稳定公共前缀放在前面、动态内容放在后面，通常更容易复用；但绝不能为了命中率破坏语义、权限或租户隔离。

10.3 SGLang RadixAttention vs vLLM APC

RuntimePrefix 索引思路共同目标
SGLangRadix-style prefix tree / longest-prefix reuse复用已经计算的精确共享前缀 KV，避免重复 Prefill
vLLMBlock-oriented APC；使用 prefix-aware block hash 查找已计算 blocks复用已经计算的精确共享前缀 KV，避免重复 Prefill

RadixAttention 是 SGLang 的具体机制/术语，不应该当作所有 Prefix Caching 的通用名称。不同 runtime 可以使用不同数据结构达到同样的跨请求前缀复用目标。

10.4 Prefix Cache ≠ Semantic Cache

CacheKey复用什么是否仍调用模型
KV / Prefix Cacheexact compatible token prefixintermediate K/V computation是：suffix / Decode 仍需执行
Exact Response Cacheexact request keyfinal response通常否
Semantic Cacheembedding / semantic similarityprior response / tool result命中时可跳过
必须区分

Prefix caching reuses computation. Semantic caching reuses an answer.

10.5 Multi-Agent：先保留边界，再优化共享前缀

Common System Policy
+ Common Tool Schema
+ Stable Safety / Formatting Rules
        ↓ shared prefix

Agent-specific Role / Skill Context
        ↓ divergence

User / Task Context

不要为了 Cache Hit 强行让所有 Agent 使用相同角色定义。先保证责任边界、权限隔离与语义正确，再优化共享前缀。

10.6 Security：Cache sharing 也是隔离策略

SHARE更高复用
更高 prefix hit rate · 更少 Prefill · 更低 TTFT；适合同一 trust group 内大量公共前缀。
ISOLATE更强隔离
通过 cache namespace / salt 限制跨用户或跨租户复用，牺牲部分命中率换取隐私边界。
vLLM CACHE SALT

vLLM 当前支持 request-level cache_salt，把 salt 混入 Prefix Cache key。不同 salt 的请求不能共享缓存 blocks，可用于降低跨租户 prefix timing side-channel 风险。

10.7 Serving Metrics：用 workload 证明收益

指标回答什么问题

10.8 面试回答

回答结构

多个 Agent 能否复用 KV Cache，要看它们是否由支持 Prefix Caching 的 serving engine 承载，以及请求是否拥有兼容且完全一致的 token prefix。没有跨请求 Prefix Cache 时会重复 Prefill；使用 SGLang Radix-style cache 或 vLLM APC 后，后续请求可以复用已计算的共享前缀 KV blocks，只计算分叉后的 suffix。这里共享的是 immutable prefix computation，不是可变会话状态。它主要优化 Prefill / TTFT，不直接减少 Decode；Semantic Cache 则是另一层的 response reuse。生产上还必须考虑 Prompt 对齐、cache eviction 和 multi-tenant isolation / cache salt。

SOURCE BOUNDARY

本章由用户提供的多 Agent KV Cache 视频总结出发，并用 vLLM、SGLang、Hugging Face 与 Redis 官方资料校正：不把“默认不能共享”当通则；区分 Prefix Cache 与 Semantic Cache；补充 token-level identity、Prefill/Decode 边界和多租户安全。
