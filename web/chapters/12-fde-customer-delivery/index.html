12

FDE 客户交付与需求工程

从模糊需求出发，通过可验证的最小闭环、验收指标与可靠交接，交付能持续运行的 AI 系统。

12.1 FDE 的完整交付链：问题到运行结果

技术交付不是“模型能回答一个示例”。应把真实工作流、数据权限、业务验收、安全降级和交接放进同一个决策链。

Ambiguous request
 → discover constraints and baseline
 → define success + non-goals
 → walking skeleton
 → evaluated thin slice
 → shadow / canary release
 → operating owner + handoff

12.2 Requirements Discovery：问能改变架构的问题

维度客户问题决定什么
结果改善谁的哪一步？对比哪个 baseline？成功指标
权限什么数据？谁能读写？身份 / RLS / VPC
失败答错与拒答哪个损失更大？HITL / gate
运行多快、多少并发、谁维护？SLO / cost / owner

记录假设时注明证据、owner、验证动作和决策时间；会议里说过不代表已确认为需求。

12.3 Walking Skeleton：优先跑通最薄的真实闭环

ONE customer identity
 → ONE authorized data source
 → ONE realistic task
 → ONE production-shaped deployment path
 → ONE trace and acceptance assertion

一份完美 Notebook 不证明集成成功。最小闭环必须尽早跨越网络、认证、数据获取、执行、可观测和回滚边界；再决定是否需要多 Agent。

12.4 Scope：把 In / Out 与验收写在同一页

项目In scopeOut of scope
用户指定的已授权支持团队公司所有团队
工作流解释一类订单异常并提供证据修改全部订单及自动退款
评估标注集、权限测试、延迟预算“展示时看起来不错”

12.5 Acceptance Contract：把正确、时延、成本、风险分开

维度指标示例对应失败
业务每个已核验任务节省的人工时间没有实际价值
质量真实样本 correct/grounded rate只在演示样本好看
安全越权读取和工具拒绝测试模型口头保证安全
可靠性p95 latency、timeout、rollback平均数掩盖尾部故障
经济性Cost per successful approved task仅优化每 Token 成本

12.6 向非工程师解释取舍：决策 / 收益 / 风险 / 证据

示例：发票精确查询优先试用 permission-filtered Exact/BM25 路径，因为来源与权限容易审计；如果评估发现同义改写召回不足，再加入 Dense 检索。不是预设 BM25 永远优于向量检索。

12.7 Live Demo 故障：透明恢复优于掩饰

时刻行动
演示前核对权限、实时服务、数据刷新时间和已知成功请求
发生故障明确失败步骤与客户影响，记录 trace
降级回放必须标记为录制/样例，不伪称实时成功
后续给出 owner、复现步骤和交付决策

12.8 Handoff：离开后系统仍能被可靠运行

交接最小集包含：数据契约、租户权限、版本化 Eval Suite、仪表盘、SLO、Incident Runbook、成本预算、发布/回滚说明、明确的值班与升级负责人。

12.9 场景演练：紧急服务响应时间

客户希望降低急救响应时间。先拆成接线、人工分诊、定位、派单、行车和记录延迟，确认决定权必须在合格的人类调度员手中。第一阶段可以是经过审核的辅助转录/信息整理，而非自动调度。

若最大的瓶颈是路况和行车时间，部署 LLM 文本助手很可能没有意义。强 FDE 会证明或否定这个假设，而不是强行套 AI 架构。
